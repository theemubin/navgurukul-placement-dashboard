## 2. Current Request Flow

1. The frontend student dashboard (`Dashboard.jsx`) mounts and triggers:
   * `statsAPI.getStudentStats()` -> `GET /api/stats/student`
   * `jobReadinessAPI.getMyStatus()` -> `GET /api/job-readiness/my-status`
2. **Current Backend Processing (No Caching)**:
   * **Stats**: Queries the `Application` collection for all documents belonging to the authenticated student, groups/filters them into status summaries, retrieves the 5 most recent entries, and returns them.
   * **Job Readiness (Expensive)**: Finds the user, queries the `JobReadinessConfig` matching the student's campus and school, merges all criteria configs, finds the student's `StudentJobReadiness` document, runs **readiness recalculations (`calculateReadiness`)**, writes/saves the updated document to MongoDB, and returns the combined response payload.

## 3. Recommended Redis Cache Keys

The existing `cacheMiddleware` at `backend/middleware/cache.js` automatically appends user scope to keys if the request is authenticated:
`cacheKey = ${prefix}:${req.originalUrl || req.url}:user:${req.user._id}`

Based on this, the recommended keys are:
* **Student Stats**:
  * **Key Format**: `cache:stats:/api/stats/student:user:<student_id>`
  * **Generated By**: `cacheMiddleware({ type: 'dashboard', keyPrefix: 'stats' })`
* **Student Job Readiness**:
  * **Key Format**: `cache:job_readiness:/api/job-readiness/my-status:user:<student_id>`
  * **Generated By**: `cacheMiddleware({ type: 'job_readiness', keyPrefix: 'job_readiness' })`

---

## 4. Recommended TTL (Time-To-Live)

We will align with the existing environment TTL configurations in `backend/.env`:
* **Student Stats**: **60 seconds** (`REDIS_TTL_DASHBOARD_STATS` env variable, fallback to 60).
* **Job Readiness**: **300 seconds (5 minutes)** (`REDIS_TTL_JOB_READINESS` env variable, fallback to 300).

---

## 5. Risks and Invalidation Strategy

* **Risk of Stale Application Stats**: If a student applies for a job, changes status, or withdraws, their dashboard stats counts (e.g. In Progress, Selected) will display outdated numbers until the cache expires or is invalidated.
  * *Mitigation*: We will use the existing `invalidateCache` helper inside the write paths of `applications.js` to immediately purge `cache:stats:*` upon any application modifications.
* **Risk of Stale Job Readiness**: If a student submits a proof file, or if a PoC approves a criterion, the student dashboard's readiness bar might show incorrect progress.
  * *Mitigation*: We will call `invalidateCache` to purge `cache:job_readiness:*` whenever criteria are updated, rated, commented on, or when the user changes profile parameters (like campus or school) in `jobReadiness.js` and `users.js`.
